# План: переводчик как сервис — сервер + клиент (06.10.2026)

Цель: раскатать конвейер на сервере и раздать пользователям клиент, как у конвертера P&ID.
Переводчик должен улучшаться от постоянной работы, эксперт — иметь доступ для ручного улучшения.

## Принятые решения (Максим, 06.10)

| Вопрос | Решение |
|---|---|
| Связь с конвертером | Отдельный сервис и отдельный клиент. Свой docker-compose на том же сервере, своя сборка клиента |
| Токен портала | Личный токен каждого пользователя: вписывается в клиент, сервер переводит этим токеном |
| Доступ | Учётные записи с ролями: пользователь / эксперт / админ |
| Автопополнение | Только через эксперта. Правка сразу действует в переводе её автора и попадает в общую память с пометкой «не подтверждено». Для остальных правка, как и обязательный термин, начинает действовать после решения эксперта |

Образец — конвертер (`C:\project\pid_pipeline_deploy`). Что у него берём:
- сервер: docker-compose, FastAPI, Celery, Redis, Postgres;
- клиент на PySide опрашивает сервер по таймеру;
- клиент собирается PyInstaller в zip, рядом лежит `client.cfg` с адресом сервера.

Чего у конвертера нет и что делаем впервые: вход и роли, единая тема оформления, настоящий процент прогресса.

## Устройство

```
hu_translate/
  src/        движок — готовый конвейер (pipeline.py и модули)
  server/     FastAPI: учётные записи, проекты, задачи, вычитка, глоссарии; Celery-задача перевода
  client/     PySide6: вход, задачи, вычитка, экспертный режим, тема оформления
  docker/     Dockerfile, docker-compose.yml, .env.template, скрипты выката и приёмки
```

### Сервер (docker-compose, имя проекта `hut`, своя сеть, порт API 8010)

**Сервисы:**
- **api** — FastAPI;
- **worker** — Celery, параллельно N задач разных пользователей;
- **redis** — брокер очереди и временное хранение токенов;
- **postgres** — пользователи, проекты, глоссарии, память переводов, задачи, правки.

Образ: python-slim + tesseract-ocr-hun, около 0,5 ГБ, без torch.

**Задача перевода:**
- Файлы, проект и токен из заголовка запроса превращаются в задачу Celery. Задача по шагам вызывает функции `pipeline.py`.
- Задачи одного пользователя идут строго по одной: замок в Redis по хэшу токена. Два прогона на одном токене портал не держит, отвечает «200 без choices».
- Задачи разных пользователей идут параллельно, каждая в пределах лимитов своего токена.
- Прогресс настоящий. В конвейер добавляется обратный вызов `progress(шаг, сделано, всего)`, задача пишет его в БД не чаще раза в несколько секунд. Время до готовности считается по текущей скорости.
- Отмена: флаг задачи проверяется между разделами.
- Обрыв (перезапуск воркера, истёк токен) переводит задачу в статус «ждёт продолжения». Продолжение стоит дёшево, потому что ответы портала в кэше.
- Жёсткий лимит времени Celery не ставить: комплект идёт часами. Включить `acks_late`.

**Токен пользователя:**
- **В клиенте:** хранится в системном хранилище паролей (keyring: Windows Credential Manager). На Astra, где хранилища может не быть, — файл, доступный только владельцу.
- **На сервер** токен уходит только при создании или продолжении задачи.
- **На сервере** — в Redis, зашифрованный ключом сервера, со сроком жизни задачи. В Postgres и в логи не пишется. Удаляется, когда задача закончилась.
- **Проверка:** кнопка «Проверить токен» делает дешёвый запрос к порталу.
- **Риск:** токены проходят через сервер. Нужен как минимум HTTPS внутри сети: обратный прокси с внутренним сертификатом.

**Глобальное состояние движка** — переделать до того, как задачи пойдут параллельно:
- `llm._TOK` кэширует токен на весь процесс. Нужно `llm.set_token()` в начале каждой задачи.
- `segments.OCR_DIR` и `review_portal.configure()` — глобальные переменные модулей.

Решение: Celery в режиме prefork, одна задача на процесс-потомок, сброс состояния в начале задачи.

**Кэш портала:**
- общий для всех: одинаковый запрос даёт одинаковый ответ, и повторы бесплатны;
- чистка по возрасту (например, старше 60 дней) или по объёму.

**Диск:**
- ротация логов у всех сервисов — урок конвертера: логи CVAT съели 9 ГБ;
- лимит кэша;
- ежедневный `pg_dump`. Глоссарии и память переводов — главная ценность, их потеря невосполнима.

### Данные (Postgres)

- `users`: логин, имя, хэш пароля (argon2), роль, активен.
- `projects`: имя, предметная область (фраза для промпта), текущая версия глоссария.
- `glossary_entries`:
  - проект, слой (`customer` / `expert` / `candidate`), hu, ru, комментарий, «строгий»;
  - источник (импорт / новый комплект / правки / конфликт), примеры в контексте, частота;
  - кто предложил, кто и когда решил.
- `tm_entries`: проект, венгерский ключ, русский текст, статус (`unconfirmed` / `approved` / `rejected`), автор, кто утвердил, задача-источник.
- `jobs`:
  - владелец, проект, статус, шаг, сделано/всего, время до готовности;
  - версия глоссария, на которой шёл перевод — по ней потом измеряется рост качества;
  - время, ошибка.
- `edits`: задача, документ, сегмент, hu, было, стало, автор, время. Это журнал правок и сырьё для автопополнения.
- `job_stats`: сегментов, формальных замечаний, подозрений проверки, автоисправлений, правок редактора. Из этой таблицы строится панель качества.

Сегменты и переводы задачи остаются в JSON движка: `storage/jobs/{uid}/json`. Глоссарий перед каждой задачей
выгружается из БД снимком в md-файлы формата движка. Движок менять не нужно, а перевод воспроизводим по версии глоссария.

### Клиент (PySide6)

1. **Вход.** Адрес сервера берётся из `client.cfg`, дальше логин и пароль. В настройках — поле токена портала и кнопка «Проверить».
2. **Главное окно:**
   - выбор проекта и большая кнопка «Новый перевод»;
   - список моих переводов: документы, статус, полоса прогресса, время до готовности, место в очереди;
   - кнопки «Открыть вычитку», «Открыть папку», «Скачать снова», «Отменить».
3. **Новый перевод:**
   - файлы перетаскиванием или кнопкой «Выбрать файлы»;
   - проект;
   - папка сохранения (запоминается);
   - переключатель «смысловая проверка».

   Готовый результат сам скачивается в выбранную папку.
4. **Вычитка:**
   - вкладки по документам, таблица «оригинал | перевод»;
   - подсветка как в xlsx: красный — формальная ошибка, оранжевый — подозрение по смыслу, голубой — изменено автоматически, жёлтый — не найден термин;
   - фильтры-чипы: Все / Ошибки / Подозрения / Изменено автоматически / Термины;
   - боковая панель: термины глоссария этой строки, причина подозрения, «было: …»;
   - правка прямо в ячейке уходит на сервер. Сервер разносит её по одинаковым и похожим строкам, и те обновляются в таблице.
   - Кнопка «Пересобрать и скачать». Выгрузка в xlsx остаётся для внешних редакторов.
5. **Экспертный режим** (роль «эксперт»):
   - **Кандидаты** — карточки: предложение hu → ru, откуда взялось, примеры в контексте, частота, сколько разных людей. Кнопки: принять / исправить / отклонить / сделать строгим.
   - **Глоссарий** — поиск и правка по слоям. Импорт глоссария заказчика из docx/xlsx/md с предпросмотром расхождений с текущим.
   - **Память переводов** — неподтверждённые фразы: утвердить / отклонить.
   - **Конфликты** — один венгерский термин переведён по-разному.
   - **Качество** — графики по месяцам и версиям глоссария: доля строк, которые правит редактор; доля подозрений проверки; повторы.
6. **Админ:** пользователи — создать, назначить роль, сбросить пароль.
7. **Оформление:**
   - один модуль `client/theme.py`: цветовые токены, отступы, шрифты, генерация QSS; светлая тема, тёмная — по желанию;
   - SVG-иконки в комплекте;
   - цвета подсветки совпадают с xlsx.

   У конвертера оформление разбросано по 27 файлам, здесь оно с первого дня в одном месте.
8. **Раздача** — как у конвертера (`deploy_ready/build_client.ps1`): PyInstaller-сборка под Windows и Astra, zip и `client.cfg`.
   Сервер отдаёт `/api/version`, клиент показывает «доступна новая версия» со ссылкой.

## Автоулучшение

**Откуда берутся кандидаты в термины:**
1. **Каждый новый комплект.** После задачи токеном её владельца запускается предпроход `terms`: частые сочетания вне глоссария, переведённые порталом. Кандидаты копят частоту от комплекта к комплекту, дубли склеиваются.
2. **Правки редакторов.**
   - Тройка «оригинал, было, стало» уходит порталу коротким запросом: «какой термин заменён на какой».
   - Получается кандидат с числом подтверждающих правок и числом разных авторов.
   - Многократная замена одного слова на другое поднимает его в очереди.
3. **Конфликты.** Один венгерский термин в утверждённой памяти и правках переведён по-разному.
4. **Замечания проверки** со ссылкой на термин повышают приоритет кандидата.

**Правила:**
- **Без эксперта** ничего не становится обязательным для всех.
- **Решение эксперта** повышает версию глоссария, и следующие задачи идут уже с ним.
- **Неподтверждённая память** действует только в задачах её автора, утверждённая — у всех.
- **Измерение.** «Улучшается» значит, что от версии к версии глоссария падает доля правок редактора на 1000 строк.
  Свежий замер — ежемесячная слепая выборка по образцу стенда.

**Глоссарий заказчика** импортируется в слой `customer` и становится основой проекта.
- В архиве «Пакша» глоссарий пришёл и в docx (`_Глоссарий HU-RU.docx`), и в md (`glossary_FAT.md` — надмножество docx).
- md читается движком как есть.
- Для заказчиков, которые пришлют только docx или xlsx, нужен разбор таблиц. Его проверка: импорт `_Глоссарий HU-RU.docx` должен дать подмножество `glossary_FAT.md`.

## Шаги и приёмка

| Шаг | Что | Приёмка |
|---|---|---|
| 0 (Максим) | Сервер видит портал: `curl -sI https://go.ai-rosatom.ru` с сервера; свободны порт 8010 и ≥10 ГБ диска | ответ портала, а не таймаут |
| 1 | Движок готов к сервису: `progress`, `set_token`, сброс состояния, отмена. Сервер: вход и роли (админ создаёт учётки командой), API задач (создать, статус, отменить, скачать zip), замок по токену. Глоссарий пока из файлов проекта | через curl: вход → загрузка пробного комплекта → прогресс → zip побайтно как у CLI |
| 2 | Клиент: вход, токен, «Новый перевод», список с прогрессом, автоскачивание, тема | exe из скрипта сборки переводит пробный комплект от начала до конца |
| 3 | Вычитка в клиенте: таблица, подсветка, фильтры, боковая панель; API правок → память (неподтверждённая) + разнос по похожим + пересборка | правка в клиенте разошлась по похожим строкам и попала в DOCX |
| 4 | Глоссарии в БД по слоям и версиям, импорт глоссария заказчика, экспертный режим (кандидаты, конфликты, утверждение памяти), снимок для движка | импорт docx заказчика даёт подмножество `glossary_FAT.md`; принятый кандидат действует в следующей задаче |
| 5 | Панель качества, сборка клиента под Astra, бэкапы, скрипты выката и приёмки (как `tools/deploy_check.sh`) | приёмка на сервере зелёная; бэкап восстанавливается |

Каждый шаг — отдельная ветка с проверкой. Шаги 1–2 дают рабочий продукт без вычитки и эксперта.
Шаги 3–4 и есть автоулучшение.

## Риски

- **Токены проходят через сервер.** Нужны HTTPS, шифрование в Redis и запрет писать токен в логи. Это проверяется тестом на логи.
- **Портал под нагрузкой.** У каждого пользователя свои лимиты, но портал общий. Если при нескольких одновременных
  задачах начнутся ответы «200 без choices», нужен общий ограничитель на весь сервер.
- **Учёба на себе.** Ошибки автоисправления (каждое десятое вносит новую) не должны попадать в память. В неё идут только
  правки человека, утверждение — у эксперта.
- **Сервер недоступен из среды разработки.** Выкат делает Максим по готовым скриптам, приёмка — скриптом проверки.
