# План: переводчик как веб-сервис (06.10.2026)

Цель: раскатать конвейер на сервере и дать пользователям веб-интерфейс. Переводчик должен улучшаться от постоянной работы.
Эксперт должен иметь доступ, чтобы улучшать его вручную.

## Принятые решения (Максим, 06.10)

| Вопрос | Решение |
|---|---|
| Связь с конвертером | Отдельный сервис на том же сервере |
| Интерфейс | Веб в браузере, ничего не устанавливается. HTMX + Tabulator. Проектирование по эвристикам Нильсена |
| Сервер | Упрощённый: один контейнер, один процесс, SQLite, очередь задач внутри приложения. Без Celery, Redis и Postgres |
| Токен портала | Личный токен каждого пользователя. Вписывается в профиле, хранится на сервере зашифрованным |
| Доступ | Учётные записи с ролями: пользователь / эксперт / админ |
| Автопополнение | Только через эксперта. Правка сразу действует у её автора. Для остальных, как и обязательный термин, — после решения эксперта |
| Приоритет | Быстро показать рабочее, как можно больше держать на Python |

## Устройство

```
hu_translate/
  src/          движок — готовый конвейер (pipeline.py и модули)
  server/       веб-приложение
    app.py        FastAPI: страницы и действия, вход, роли
    db.py         SQLite: пользователи, сессии, задачи (дальше — глоссарии, память, правки)
    jobs.py       очередь: каждая задача — отдельный процесс-исполнитель
    runner.py     исполнитель задачи: шаги pipeline.py, прогресс в progress.json
    templates/    HTML-шаблоны Jinja2 с атрибутами HTMX
    static/       htmx.min.js, pico.min.css, app.css; позже tabulator
  manage.py     команды админа: создать пользователя, сменить роль, сбросить пароль
  Dockerfile, docker-compose.yml   один сервис, настройки — строки в .env
```

### Задачи и очередь

- Каждая задача выполняется в отдельном процессе (`server/runner.py`). Глобальное состояние движка (токен, папка OCR,
  настройки проверяющего) живёт внутри процесса задачи и не смешивается между пользователями. Переделывать движок не нужно.
- Токен передаётся процессу через переменную окружения. Ни в командной строке, ни в логах его нет.
- Одновременно идёт не больше одной задачи на пользователя: два прогона на одном токене портал не держит.
  Всего — не больше `HUT_MAX_JOBS` (по умолчанию 3).
- Прогресс: движок получает обратный вызов `progress(шаг, сделано, всего)`, исполнитель пишет его в `progress.json`.
  Страница опрашивает его раз в 2 секунды. Веса шагов: извлечение 5 %, перевод 45 %, проверка 45 %, сборка 5 %.
  Время до готовности — по скорости текущего шага.
- Отмена: процесс задачи останавливается.
- Перезапуск сервера: прерванные задачи снова встают в очередь. Шаги конвейера продолжают с места, ответы портала в кэше.
- Задача хранится в `data/jobs/<uid>/`: `in/` (исходники), `work/` (json, ocr), `out/` (результат),
  `progress.json`, `log.txt`.

### Безопасность

- Пароли — `hashlib.scrypt` из стандартной библиотеки.
- Сессии — случайный идентификатор в cookie (HttpOnly) и таблица в SQLite.
- Токен портала — шифрование Fernet (`cryptography`) ключом из `.env` сервера.
- Внутри сети нужен HTTPS (обратный прокси), потому что через сервер проходят пароли и токены.

### Экраны (эвристики Нильсена: состояние на виду, язык пользователя, отмена, понятные ошибки)

1. **Вход.**
2. **Профиль:** токен портала с кнопкой «Проверить».
3. **Переводы:**
   - загрузка файлов, выбор проекта, переключатель «смысловая проверка»;
   - список задач: шаг, процент, время до готовности, место в очереди;
   - кнопки «Скачать» и «Отменить».
4. **Вычитка (шаг 2):**
   - таблица Tabulator с подсветкой (красный — формальная ошибка, оранжевый — подозрение, голубой — изменено автоматически, жёлтый — термин не найден);
   - фильтры-чипы, боковая панель с терминами и причиной;
   - горячие клавиши, правка прямо в ячейке.
5. **Эксперт (шаг 3):** кандидаты в термины, глоссарий по слоям, импорт глоссария заказчика, конфликты, утверждение памяти.
6. **Качество (шаг 4):** графики Chart.js по месяцам и версиям глоссария.

Выбор папки сохранения работает только в браузерах на Chromium (`showDirectoryPicker`), для этого нужно немного JavaScript.
В первой версии результат приходит обычным скачиванием zip.

## Автоулучшение (шаги 2–3)

**Кандидаты в термины берутся из трёх источников:**
1. После каждого комплекта — предпроход `terms`: частые сочетания вне глоссария, их сразу переводит портал.
2. Правки редакторов. Тройка «оригинал, было, стало» уходит порталу с вопросом, какой термин заменён на какой.
   Считается, сколько правок и сколько разных людей это подтверждают.
3. Конфликты: один термин переведён по-разному.

**Правила:**
- Обязательным для всех термин становится только после решения эксперта.
- Решение эксперта повышает версию глоссария, и следующие задачи идут уже с ней.
- Неподтверждённая память действует только у её автора.

Измеряется доля строк, которые правит редактор: она должна падать от версии к версии глоссария.

**Глоссарий заказчика** импортируется как основной слой проекта.
- md читается движком как есть.
- Для docx и xlsx нужен разбор таблиц. Проверка разбора: импорт `_Глоссарий HU-RU.docx` «Пакша» должен дать подмножество `glossary_FAT.md`.

## Риски

- Токены хранятся на сервере: шифрование, HTTPS, тест на то, что токен не попадает в логи.
- Портал общий. Если при нескольких одновременных задачах пойдут ответы «200 без choices», нужно снизить `HUT_MAX_JOBS`.
- Учёба на себе: в память идут только правки человека, утверждение — у эксперта. Автоисправления туда не попадают:
  каждое десятое вносит новую ошибку.
- Сервер недоступен из среды разработки. Выкат делает Максим по готовым скриптам.
