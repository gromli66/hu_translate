# hu_translate — перевод эксплуатационной документации АЭС HU→RU на портале

Переводит комплект венгерских документов (DOCX, PDF с текстом, сканы) на русский через внутренний портал
go.ai-rosatom.ru (модель `privateLLM`). Перевод возвращается в исходный формат с сохранением разметки,
плюс таблица вычитки для редактора. Наружу ничего не уходит: все запросы — только на портал.

Схема отлажена на комплекте АЭС «Пакш» (ВВЭР-440, 5 документов, 01–06.10.2026). Каждое решение в ней
проверено слепой вычиткой; цифры ниже.

Это описание для разработчика: как устроено и как запускать без Docker. Развернуть сервис и начать работу — [README](../README.md).

## Установка (разработка)

1. Python 3.11+ и зависимости: `pip install -r requirements.txt`.
2. Tesseract 5 с венгерским языком (нужен для сканов). Проверка: `tesseract --list-langs` должен показать `hun`.
3. Токен портала: файл `.env` в корне репозитория (он в `.gitignore`), строка `ROSATOM_AI_TOKEN=...`,
   или переменная окружения с тем же именем. Необязательные параметры: `ROSATOM_AI_BASE`, `ROSATOM_MODEL`, `HU_CACHE`.

## Веб-сервис

Тот же конвейер в браузере: вход по логину, личный токен портала в профиле, загрузка документов, очередь,
настоящий процент с временем до готовности, скачивание архива с переводами и таблицами вычитки. План развития —
[PLAN_service.md](PLAN_service.md).

Локальный запуск:

```bash
python -m uvicorn server.app:app --port 8010
```

```bash
python manage.py user add ivanov --name "Иванов И." --role admin
```

Сервис открывается по адресу `http://localhost:8010`. Данные лежат в `data/` (в git не попадает):
- `hut.db` — пользователи, задачи;
- `jobs/<uid>/` — исходники, рабочие файлы, результат, лог;
- `cache/` — ответы портала;
- `secret.key` — ключ шифрования токенов, если он не задан в окружении.

Как устроено:
- каждая задача выполняется отдельным процессом (`server/runner.py`), токен уходит ему через переменную окружения;
- одновременно идёт не больше одной задачи на пользователя (два прогона на одном токене портал не держит)
  и не больше `HUT_MAX_JOBS` всего;
- после перезапуска сервера прерванные задачи продолжаются с места.

**Вычитка в браузере** — кнопка «Вычитка» у готового перевода:
- **Таблица.** Оригинал | перевод с подсветкой:
  - красный — формальная ошибка;
  - оранжевый — подозрение смысловой проверки;
  - голубой — изменено автоматически;
  - жёлтый — не найден термин;
  - зелёный — правка.
- **Фильтры-чипы.** По умолчанию — «Требуют внимания».
- **Боковая панель:** причина отметки, «было» с кнопкой «Вернуть», термины глоссариев в строке.
- **Горячие клавиши:** Alt+↓ / Alt+↑ — следующая / предыдущая строка, Enter — править, Shift+Enter — сохранить, Esc — отменить.
Вычитка — правка перевода прямо в сервисе, до окончательного скачивания.

**Правка в ячейке** (Shift+Enter) сразу попадает в три места:
1. **В перевод этого документа** — во все строки с той же венгерской фразой во всех документах комплекта.
   Файлы DOCX/PDF пока прежние.
2. **В журнал правок** — кто, что и на что исправил. Из журнала считается «Качество» и собираются кандидаты в термины.
3. **В память переводов** с пометкой «не подтверждено». Действует только в следующих переводах того же редактора,
   после утверждения экспертом — у всех.

**«Применить и пересобрать файлы»:**
- похожие фразы получают правку: та же фраза с другими числами — подстановкой (без портала), похожая по смыслу —
  переводом по образцу (под токеном владельца);
- DOCX, PDF и таблица вычитки пересобираются;
- портал разбирает правки: если редактор заменил термин, эксперт увидит кандидата «Из правок».

Исправленные файлы — **«Скачать» после «Применить»**. До этого скачиваются прежние.

```
правка в ячейке ──► этот перевод (все такие же фразы)
                ├─► журнал правок
                └─► память переводов «не подтверждено» ──► эксперт утвердил ──► у всех

«Применить» ──► похожие фразы ──► файлы пересобраны ──► «Скачать»
            └─► кандидаты в термины ──► эксперт принял ──► глоссарий (со следующего перевода)
```

**Эксперт** (роли `expert`, `admin`), раздел «Эксперт»:
- **Кандидаты в термины.** Собираются сами:
  - после каждого перевода — частые сочетания вне глоссариев, их переводит портал;
  - после «Применить» — какой термин заменил редактор.

  Эксперт принимает, правит, делает «строгим» или отклоняет. Отклонённое не всплывает снова. Варианты одного термина
  показываются как конфликт. Принятый термин действует **со следующего перевода**; готовый документ не меняется
  (его можно загрузить заново — неизменённое возьмётся из кэша — или поправить во «Вычитке»).
- **Память переводов.** Неподтверждённые правки редакторов, варианты одной фразы рядом. Утверждённая фраза действует у всех.
- **Глоссарий.** Поиск по слоям. Термины эксперта можно править и удалять, глоссарий заказчика только читается.
- **Импорт глоссария заказчика** из md, docx или xlsx. Сначала показывается, что изменится, замена — только после подтверждения.
- **Справка** — инструкция эксперта прямо в сервисе: рабочий цикл, как разбирать кандидатов и конфликты, частые вопросы.

Глоссарии хранятся в базе по слоям: заказчик → эксперт → кандидаты. При первом обращении к проекту они переносятся из его файлов.
Любое решение по глоссарию повышает версию проекта. Перевод получает снимок своей версии
(`data/glossary/<проект>/v<N>/`) и запоминает её номер, поэтому рост качества можно мерить по версиям.

**Качество** (раздел «Эксперт» → «Качество») показывает по месяцам и по версиям глоссария:
- долю строк, которые правят редакторы;
- долю подозрений смысловой проверки;
- долю формальных замечаний.

Подозрения и замечания считаются сразу после перевода, до правок. Улучшение — это падение доли правок.

**Обслуживание** — сервис делает его сам раз в сутки:
- копия базы в `data/backups/` (хранится `HUT_BACKUP_KEEP`, по умолчанию 14); вручную — `python manage.py backup`;
- удаление по сроку файлов задач (`HUT_KEEP_DAYS`) и старых ответов портала (`HUT_CACHE_DAYS`). По умолчанию 0, то есть выключено. Правки, память и глоссарии хранятся в базе и при этом не удаляются.

Ограничения:
- размер одного загружаемого файла — `HUT_MAX_UPLOAD_MB`, по умолчанию 200;
- вход — после 5 неудачных попыток пауза 10 минут.

Пользователи (`python manage.py user …`): `add`, `role`, `passwd`, `disable`, `enable`, `list`. Роли: `user`, `expert`, `admin`.
Админ видит задачи всех пользователей.

### Выкат на сервер

Развёртывание — в [README](../README.md): `git clone` и `docker compose up -d --build`. Настройки (`HUT_MAX_JOBS`,
`HUT_MAX_UPLOAD_MB`, `HUT_BACKUP_KEEP`, `HUT_KEEP_DAYS`, `HUT_CACHE_DAYS`, `HUT_COOKIE_SECURE`, `HUT_SECRET_KEY`, порт
`HUT_PORT`) задаются строками в `.env` рядом с `docker-compose.yml`; без них действуют значения по умолчанию, ключ
шифрования создаётся сам в `data/secret.key`.

Внутри сети сервис стоит закрыть HTTPS (обратный прокси) и выставить `HUT_COOKIE_SECURE=1` в `.env`: через него
проходят пароли и токены.

## Проект

Проект — это папка `projects/<имя>/` с файлом `project.json` (пути указываются относительно него):

```json
{
  "glossary": "data/glossary_FAT.md",
  "terms": "data/komplekt_terms.md",
  "conventions": "data/CONVENTIONS.md",
  "tm": "data/tm.json",
  "rules": "data/conventions.json",
  "doc_terms": "data/doc_terms"
}
```

| Поле | Что это | Обязательно |
|---|---|---|
| `glossary` | основной глоссарий заказчика; у него высший приоритет | да |
| `terms` | глоссарий комплекта; записи с пометкой «строгий» обязательны: перевод без них уходит на повтор | нет |
| `conventions` | свод принятых соответствий для смысловой проверки (раздел `## Уже принято` или весь файл) | нет |
| `tm` | память переводов: утверждённые редактором фразы. Создаётся командой `edits` | нет |
| `domain` | первая фраза системного промпта переводчика, если документы из другой области | нет |
| `rules` | языковые соглашения, машинно проверяемые (JSON): ссылки, латиница, сокращения, предупреждение — для шлифовки | нет |
| `doc_terms` | папка словарей документов `<имя документа без расширения>_terms.json` — для шлифовки; нет словаря — только `rules` | нет |

Формат глоссария — markdown. Раздел `## Правила применения` целиком уходит в промпт. Записи — строки таблиц
`| Венгерский | Русский | Комментарий |` в любых разделах. Внутри венгерской ячейки действуют соглашения:

- `A / B` — варианты одного термина;
- `nem X / X` — остаётся только отрицательный вариант;
- `… ` — пропуск слов внутри термина;
- `(…)` — пояснение, термином не считается.

Данные проектов (`projects/*/data/`) в git не попадают: это материалы заказчика.

## Запуск

```bash
python translate_komplekt.py run путь/к/документам --project projects/paks/project.json --work work/paks
```

Результат появляется в `work/paks/out/`:
- `<док>_RU.docx` или `<док>_RU.pdf` вместе с `<док>_RU.docx` (для PDF — ещё и DOCX: у размеченного PDF — по
  разметке, у остальных — по раскладке);
- `<док>_вычитка.xlsx` (после шлифовки — с листами «шлифовка» и «нарушения»).

Шаги можно запускать и по отдельности: `extract`, `translate`, `review`, `polish`, `assemble`. Они продолжают с того места,
где остановились. Ответы портала кэшируются в `cache/`, поэтому перезапуск после обрыва почти бесплатный.
Добавленный в комплект документ переводится той же памятью: одинаковые фразы получают одинаковый перевод.

Ключи:
- `--workers 4` — одновременных запросов перевода;
- `--review-workers 6` — одновременных запросов смысловой проверки;
- `--no-review` — без смысловой проверки (быстрее примерно вдвое);
- `--redo` — перевести заново уже переведённые документы.

Портал — узкое место. Больше потоков под нагрузкой не ускоряет (замер 05.10).

## Что происходит внутри

1. **Извлечение.**
   - DOCX: все абзацы всех частей документа (тело, таблицы, врезки, колонтитулы). Смена начертания внутри
     абзаца помечается метками `<fN>`, табуляции и переносы — `[TAB]`/`[BR]`.
   - PDF с текстовым слоем: блоки с рамками. Невидимый текст (под фоновой картинкой, слой OCR) не берётся;
     маркер пункта («•», «o», «–») — отдельно от текста пункта; значок внутри строки рвёт строку.
   - Скан: Tesseract (hun) читает слова с рамками, портал читает страницу по картинке. Коды, прописные и
     спецзнаки берутся у портала, строчные слова — у Tesseract (ошибки двух чтецов не пересекаются).
     Страница идёт как скан, только если в текстовом слое нет >15 % настоящих слов Tesseract ни по месту, ни по
     написанию; слова внутри картинок меньше половины листа (скриншоты, логотипы) не считаются.
   - Надписи на скриншотах (`src/shots.py`): Tesseract по увеличенной картинке (прямо и негативом) + детектор строк
     текста → портал по картинке исправляет неуверенное чтение и называет язык каждой надписи; в перевод — только
     венгерские (английские окна, коды, имена, даты — нет) → обычные сегменты с пометкой «Надпись на скриншоте» в
     таблице вычитки. Логотипы (с маской прозрачности), трафареты и картинки от половины листа не трогаются.
     - Детектор — PP-OCRv4 det (PaddleOCR, Apache-2.0) через OpenCV DNN; модель лежит в репозитории
       (`src/models/ch_PP-OCRv4_det_infer.onnx`, 4,7 МБ, sha256 `d2a7720d…f49da9`, взята из
       `rapidocr_onnxruntime` 1.4.4). Новых pip-зависимостей нет: OpenCV уже ставит pdf2docx, проверено на OpenCV
       4.11 и 5.0. Картинка увеличивается в 1,5 раза (не больше 2,5 Мп): ~0,5 с на скриншот, память ~0,7 ГБ. Сеть
       одна на процесс, расчёт — под замком (OpenCV DNN не потокобезопасен).
     - Рамки детектора, не накрытые словами Tesseract, дочитывает тот же Tesseract: вырезки (бинаризация Otsu,
       высота ~40 px) прямо и негативом, столбиком на одном листе, один вызов на скриншот. У варианта со светлым
       фоном стираются почти сплошь тёмные строки и столбцы у краёв (рамка выделенной вкладки или кнопки: в
       рамке Tesseract надпись не читает) — линиями, не связными областями: акцент «Á» касается линии шапки
       таблицы, и область уносила букву. Короткое неуверенное чтение (значок, крестик окна, разделитель вкладок)
       отбрасывается. Слово вырезки вытесняет неуверенный
       мусор Tesseract («ém]» во всю кнопку «Mégsem»), но не похожее на себя неуверенное слово: верное, но
       неуверенное чтение должен иметь возможность поправить портал.
     - Слова собираются в строки по близости середин, а не по округлению высоты: иначе фраза рвалась
       («Ideiglenesen | lezár», «A fejezet | indítása sikertelen!»).
     - Ответ портала разбирается по объектам: оборванный ответ отдаёт всё, что успел. Объект, который не
       разбирается как JSON (модель пишет прямые кавычки внутри строки: «„W aktiv", „Y aktiv" lassú…»),
       разбирается по ключам — текст надписи между `"t": "` и `", "lang"`; фигурные скобки в тексте (GUID) объект
       не рвут. Модель иногда сама уходит в рассуждения и обрывает ответ на 6000 токенах (UTS: 2 из 71
       скриншота) — недостающие надписи переспрашиваются дозапросом; оборвался и он — снова, пока дозапрос
       прибавляет надписи, но не больше трёх раз. Раньше обрыв терял все надписи картинки, а повторный обрыв —
       остаток (UTS стр. 26: из 51 надписи 10 + 19 за два ответа).
     - Если OpenCV не может загрузить модель, надписи ищет один Tesseract, в stderr пишется
       «shots: детектор надписей отключён — …».
     - Замер 15.10 на 14 скриншотах UTS (ручная разметка, 105 венгерских надписей): после портала найдено и
       прочитано верно 103 надписи (98 %), было 87 (83 %); лишних принятых порталом надписей не прибавилось.
       Разметка, скрипты и результаты — `work/uts_2026-10-15/shots_bench/` (не в git: скриншоты заказчика).
   - Размеченный PDF (экспорт Word со `StructTreeRoot`, без сканов): если текст дерева разметки покрывает ≥90 %
     уникальных текстов страниц (`docx_build.coverage`; UTS — 99,2 %), DOCX будет собран по разметке (см. раздел
     «DOCX по структуре PDF…»), pdf2docx не нужен.
   - DOCX для остальных PDF без сканов (`src/docx_src.py`): pdf2docx по оригиналу (в отдельном процессе), абзацы
     сопоставляются с сегментами PDF; несопоставленные переводятся своими сегментами.
2. **Перевод разделами.**
   - Документ режется на разделы ≤6000 знаков. Разделы идут по порядку, в контексте — предыдущий раздел вместе
     со своим переводом. Длинные документы режутся на потоки по ~250 тыс. знаков, 4 потока параллельно.
   - Общая память комплекта: одна фраза — один перевод. Строки, которые отличаются только числами
     (≤120 знаков), переводятся один раз, числа подставляются.
   - В запросе только те термины глоссариев, что найдены в тексте раздела, и разбор слов с отрицающими морфемами.
   - Размеченный PDF, шаг «структура» (`pipeline.struct_fill`): пробная сборка DOCX по разметке находит абзацы,
     которых нет среди сегментов страниц (абзац со ссылкой Word из нескольких элементов дерева, «FIGYELEM!» жирным +
     текст, пункт с командой Consolas). Они переводятся порталом (сначала — память переводов проекта) и становятся
     своими сегментами: дальше проверка, шлифовка, таблица вычитки и правки редактора — как у всех. Моноширинная
     часть такого абзаца без венгерских букв (команда, путь, вывод программы) остаётся дословно — и в сегменте, и в
     DOCX (`docx_build.code_part`): портал переводил `sync` → «синхронизировать» (UTS, 15.10); заполнитель
     `<beállítani kívánt IP cím>` переводится, но в тех же угловых скобках (портал их терял).
3. **Проверки кодом.** Каждый сегмент проверяется на:
   - пропуск, метки, `[TAB]`/`[BR]`;
   - коды и числа (единицы измерения переводиться могут: `400KV` ↔ `400 кВ`);
   - остатки венгерского;
   - перевёрнутые действия (открыть/закрыть, вкл/выкл, пуск/останов, нагрузка/разгрузка);
   - потерянные отрицания;
   - строгие термины комплекта.

   Не прошёл проверку — повтор с перечнем замечаний, до двух раз.
4. **Постобработка.** Единицы (`mg/dm3` → `мг/дм³`), регистр (ПРОПИСНЫЕ формулы оригинала), правило первого
   употребления аббревиатуры: «СУЗ (SZBV)», дальше просто «СУЗ».
5. **Смысловая проверка.**
   - Агент портала получает:
     - соседние строки;
     - свод соглашений;
     - термины;
     - разбор отрицаний;
     - задание пересказать смысл по-английски и сверить элементы (оборудование, действия, условия, числа,
       отрицания).
   - При серьёзной ошибке агент сразу даёт исправленный перевод. Исправление проверяется ещё раз и принимается,
     только если ошибки больше не видно и формальных замечаний не больше, чем было.
   - Вердикт выносится один раз на каждую уникальную пару «оригинал — перевод» и применяется ко всем её копиям.
6. **Шлифовка** (`pipeline.polish`, шаг «шлифовка»): языковые соглашения комплекта (`rules`) и словарь документа
   (`doc_terms`) — код, затем портал, не больше 3 проходов (подробно — раздел «DOCX по структуре PDF…»). Для всех
   документов задачи, не только PDF. Правки редактора и память переводов проекта не трогаются; одинаковая пара
   «оригинал — перевод» шлифуется один раз. Перевод заново (`--redo`) — шлифовка заново.
7. **Сокращение под место** (`pipeline.fit`). Где в PDF перевод ужимается мельче 0,7 исходного кегля, портал даёт
   короткую формулировку; код проверяет, что коды и числа те же. Только для PDF, в DOCX и таблице вычитки — полный
   перевод (в колонке H — пометка). Правка редактора сокращение отменяет.
8. **Сборка.**
   - DOCX из DOCX: перевод на месте, начертание сохраняется.
   - PDF: исходный текст убирается, перевод вписывается в рамку абзаца; у таблицы (меньше половины листа) один
     кегль на все ячейки; скриншоты заменяются переведёнными.
   - DOCX из размеченного PDF: по дереву разметки и профилю оформления оригинала (`assemble.build_struct_docx`),
     перевод — из сегментов задачи, скриншоты — переведённые. Готовый DOCX проверяется: оформление против профиля
     и соглашения по русскому тексту — в лист «нарушения». Сбой — DOCX прежним путём из переведённого PDF, причина
     в отчёте сборки (`fallback`).
   - DOCX из остальных PDF без сканов: из оригинала с переведёнными скриншотами — настоящие таблицы Word (строка
     растёт под русский текст), шрифты оригинала, пункты списков отдельными абзацами, штамп листа — в нижнем
     колонтитуле. DOCX из PDF со сканами — прежним путём, из переведённого PDF.
   - Таблица вычитки; после шлифовки — с листами «шлифовка» и «нарушения», в колонке H — «Шлифовка (правило;
     код/портал), было: …».
9. **Проверка вёрстки порталом** (по желанию): `python tools/layout_qa.py <оригинал.pdf> <перевод.pdf> <out.json>` —
   список страниц с подозрением на наложения, обрезку, мелкий кегль, непереведённое, артефакты. Подсказка, какие
   страницы смотреть глазами: на старом выводе UTS отмечены 7 из 8 испорченных страниц, ложных тревог нет.

## Работа редактора

Таблица `<док>_вычитка.xlsx`: оригинал, перевод, замечания, колонка **G** для правки, колонка **H** с итогом
смысловой проверки.

| Цвет | Значит |
|---|---|
| красный (вся строка) | не прошла проверку кодом — смотреть обязательно |
| оранжевый (D, H) | смысловая проверка подозревает искажение, причина в H |
| голубой (D, H) | перевод изменён автоматически: исправлен по замечанию проверки или по образцу правки редактора; в H — «было: …» |
| жёлтый (F) | не найден термин основного глоссария (мягкое замечание) |

Редактор вписывает правильный перевод в колонку G, сохраняет файл на том же месте и запускает:

```bash
python translate_komplekt.py edits --project projects/paks/project.json --work work/paks
```

Что делает команда:
1. Правка разносится по всем одинаковым фразам комплекта и записывается в память переводов проекта (`tm`):
   следующие комплекты возьмут эту фразу без модели.
2. Та же фраза с другими числами (например, колонтитул с номером страницы) получает правку подстановкой чисел,
   без запросов к порталу. Похожие фразы (сходство ≥0,8) переводятся заново, с утверждённой парой в роли образца.
   И те, и другие помечаются голубым. Вариант, у которого после замены стало больше замечаний проверки, не меняется.
3. Документы и таблицы пересобираются. Колонка G новой таблицы пустая; файл редактора сохраняется как есть
   в `out/правки_редактора/<время>/`.

## Новый комплект: термины

```bash
python translate_komplekt.py terms путь/к/документам --project … --work … --out terms.md
```

Команда собирает частые 1–3-словные сочетания вне глоссария и переводит их порталом в контексте. Список
проверяет специалист: правит переводы, ставит пометку «строгий» там, где термин обязателен, затем подключает
файл как `terms`. Без пометок обязательны все записи файла.

## Качество (слепые вычитки, комплект «Пакш»)

- Свежая выборка, 170 строк: **78 % верных** против 71 % у предыдущей схемы (пачки по 25 сегментов, проверка и
  исправление отдельными проходами). Единообразие лучше, серьёзных ошибок примерно столько же.
- Перевод разделами со своим контекстом: 82 % верных против 77 % у пачек, связность лучше в 5 кусках из 6.
- Автоисправление вдвое снижает число серьёзных ошибок среди отмеченных строк. Примерно каждое десятое
  исправление вносит новую ошибку, поэтому исправленные строки выделены голубым.
- Перевод по образцу правки редактора: из 92 похожих фраз лучше стало 41, хуже 1. На уникальных фразах пользы нет.
- Смысловая проверка находит 50–65 % ошибок. Хуже всего — остаточные ошибки лучшего варианта. Вычитка
  человеком обязательна.
- Отличие от замера: при замере у проверяющего был ещё второй, независимый перевод (старая схема пачками).
  Этот пакет второго перевода не делает (в два раза дороже). Насколько проверка без него хуже, не измерено.

## DOCX по структуре PDF, профиль документа и шлифовка

Для PDF, экспортированного из Word с разметкой (`StructTreeRoot`), DOCX собирается по логике документа, а не по
положению строк: стили, настоящие списки, автонумерация заголовков, оглавление и список рисунков полями Word.
Требование заказчика (15.10): «как будто писали по-русски в Word, взяв за основу оформление оригинала». Встроено
в конвейер и веб-сервис (15.10): извлечение узнаёт размеченный PDF, шаг «структура» переводит абзацы разметки без
пары в сегментах, шаг «шлифовка» правит переводы, сборка (`assemble.build_struct_docx`) даёт DOCX и проверяет его.
Сценарий `work/uts_2026-10-15/struct/build_ru.py` остался для опытов.

1. **Чтение** — `docx_struct.load`: блоки по дереву разметки. Списки перестраиваются по месту пунктов на листе и
   номерам из текста: на стыке страниц Word путает вложенность, а номер пункта кладёт прямо в текст.
2. **Профиль оформления** — `docx_profile.extract`: снимается с оригинала, для каждого документа свой. Это шрифт
   ролей (заголовки 1–5, текст, подпись, код, таблица), выключка, шаг строк и интервалы, заголовок 1 с новой страницы,
   расстояние номер → текст заголовка, отступы пунктов по уровням, рисунки и подписи, рамка, заливка и поля таблиц.
   Сборщик (`docx_build.Builder(..., profile)`) берёт значения из профиля; без профиля — значения UTS.
3. **Шлифовка** — `polish.run` (в конвейере — `pipeline.polish`): проверка по языковым соглашениям комплекта
   (`conventions.json` проекта, поле `rules`) и словарю документа (`<документ>_terms.json` в папке `doc_terms`
   проекта) → правка кодом всего однозначного → правка порталом только формулировок (лишь задетые сегменты,
   нарушенное правило в задании) → повторная проверка. Не больше 3 проходов.
4. **Проверка готового DOCX** — `docx_profile.check` (оформление против профиля, прямой кегль и отступы) и
   `conventions.check_text` (то, что видно по русскому тексту).

Правила соглашений (`src/conventions.py`): Я0 HTML-сущности, Я2 «рисунок N» в падеже, Я3 «(см. раздел N)»,
Я4 «ёлочки», Я5 названия латиницей, Я6 коды дословно, Я7 сокращения комплекта, Я8 «ВНИМАНИЕ!», Я9 даты как в
оригинале, Я10 словарь документа, Я11 венгерские слова в переводе. Словарь документа задаёт `hu` (где искать в
источнике), `ru` (как надо), `bad` (что нельзя), а также `swap` или `drop` (замена кодом).

Таблица вычитки получает листы **«шлифовка»** (каждая правка: было → стало, правило, кто правил — код или портал)
и **«нарушения»** (что осталось после цикла и проверки DOCX).

**Словарь документа.** Лежит в `projects/<проект>/data/doc_terms/<имя документа без расширения>_terms.json`
(UTS — `000018J00073_UTS_UserManual_terms.json`, утверждён Максимом 15.10). Нет словаря — шлифовка только по
соглашениям комплекта. Для нового документа словарь пока составляет человек. Предложение (не сделано): после перевода
`termx.candidates` по сегментам документа даёт частые сочетания вне глоссариев; для каждого собираются русские
переводы фраз, где оно встречается; если у сочетания два и больше разных русских соответствия (по основам слов),
получается черновая запись `{"hu": основа, "ru": преобладающий вариант, "bad": остальные варианты}`. Черновик
утверждает эксперт (в сервисе — рядом с кандидатами в термины), затем шлифовка запускается заново (`polish` после
удаления `polish` из JSON документа).

## Известные ограничения

- Должности. «főgépész», «gépész» модель переводит буквально («главный инженер», «механик»), а не принятыми
  в комплекте названиями. Лечится строгими записями в `terms`.
- Аббревиатуры в длинных перечнях иногда выпадают (ÁOKU).
- Вёрстка PDF с текстовым слоем (UTS, 15.10):
  - PDF «на месте» не раздвигает строки: пункт списка, ставший по-русски на строку длиннее, ужимается (или
    сокращается порталом); DOCX эту проблему не имеет;
  - шапка таблицы с заливкой по строкам («Fejlesztő / környezet») переводится по строкам: граница заливки
    неотличима от линейки (в формах 30RDGT заливка — единственный разделитель ячеек);
  - DOCX длиннее оригинала (UTS: строки таблиц растут под русский текст, хвост листа переходит на следующий);
  - надписи скриншотов: уверенно, но не до конца прочитанное слово Tesseract («MEGKEZDE» вместо «MEGKEZDETT»)
    портал не исправляет (уверенное чтение он не переписывает) — переводится обрубок; надпись, которую не нашли ни
    Tesseract, ни детектор, остаётся венгерской; не влезшая в своё место надпись остаётся оригинальной;
  - что переводить на скриншоте, решает язык надписи, который называет портал: в перевод — только венгерские.
    Прежний вопрос «переводить ли» портал решал через раз (UTS 15.10: английские окна VirtualBox, вход SUSE,
    веб-страница Softing то переводились — до 72 надписей за прогон, — то нет); язык он называет устойчиво: 0
    английских надписей в 4 прогонах без кэша, на 14 размеченных скриншотах верно 104/105 в обоих прогонах стенда
    (`work/uts_2026-10-15/shots_bench/README.md`, «Английские окна»). Цена: окно целиком не учитывается —
    венгерская надпись в английском окне (значок «Lomtár» на рабочем столе) переводится, английская в венгерском —
    нет; немецкие окна тоже не переводятся; венгерские имена пользователей («TesztAdminisztrátor») уходят в перевод;
  - надписи скриншотов теряются, когда портал оборвал ответ и все три дозапроса или дозапрос не прибавил ни одной
    надписи (модель уходит в рассуждения, ~1 обрыв на 45 вызовов; двойной обрыв в замере UTS — 2 раза на 18
    прогонов, до 6 надписей картинки, — теперь добирается следующим дозапросом: прогон с ним новым кодом — 104/105
    вместо 98); объект с прямыми кавычками внутри строки разбирается, только если ключи в порядке промпта
    (n, t, lang); портал сливает соседние строки в одну надпись (UTS стр. 25, 36).
- Сканы форм:
  - рукописное (подписи, даты, фамилии) намеренно не переводится и остаётся как в оригинале;
  - подпись поля, которую Tesseract склеил с рукописью в одно слово («29/7.ot2dNév:»), остаётся по-венгерски;
  - длинные русские подписи в тесных ячейках ужимаются мельче оригинала.

  Стенд проверки вёрстки: `python tools/layout_bench.py <папка с PDF> <рабочая папка>`.
- Повтор упавших сегментов идёт поштучно и даёт около 70 % запросов. Пакетный повтор в пределах раздела —
  очевидное ускорение, пока не сделано.
- Промпты настроены на эксплуатационную документацию АЭС с ВВЭР-440.

## Утечка данных

Документы уходят только на внутренний портал. Плотный глоссарий комплекта «Пакш» (`komplekt_terms.md`) собирали
агенты вне контура, читавшие документы целиком, с разрешения владельца. Для комплекта, который нельзя выносить
за контур, глоссарий комплекта строится командой `terms` (только портал) и проверяется специалистом.
